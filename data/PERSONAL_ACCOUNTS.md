# Personal movie accounts: setup and review

This change implements Google sign-in, private profiles, watched history, watchlists, and personal 1–10 ratings. The committed SQL is **a proposal only**. No Supabase project, OAuth provider, or remote schema was changed while developing this PR. Without the three account environment values below, sign-in is visibly unavailable and personal APIs return no stored data.

## Before enabling accounts

1. Create or choose a Supabase project. Review [the migration](../supabase/migrations/20261012_personal_movie_profile.sql) line by line, including the `auth.users` trigger, grants, RLS policies, constraints, and existing-user backfill. Obtain explicit approval for the live schema change before applying it manually in Supabase SQL Editor or a controlled migration runner. Confirm the migration succeeds in a nonproduction project first. This PR does not run it.
2. In Google Auth Platform, create a **Web application** OAuth client. Add the application's exact origin to Authorized JavaScript origins. Add the Supabase Google provider's callback URL, usually `https://<project-ref>.supabase.co/auth/v1/callback`, to Authorized redirect URIs. Enter the Google client ID and secret **only in Supabase's Google provider settings**, never in this repository. See [Supabase's Google instructions](https://supabase.com/docs/guides/auth/social-login/auth-google).
3. In Supabase Authentication → URL Configuration, set Site URL to the application origin and add the exact application callback URL `https://<your-host>/auth/callback` to the redirect allowlist. For local development, use `http://localhost:3000` and `http://localhost:3000/auth/callback` instead. The app sends the post-login destination in a short-lived, HttpOnly cookie, so the callback allowlist entry needs no query wildcard. See [redirect URL guidance](https://supabase.com/docs/guides/auth/redirect-urls).
4. Put these values in ignored `.env.local` and the deployment's secret/config store: `NEXT_PUBLIC_SUPABASE_URL` (project URL), `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (publishable key, **not** a service-role/secret key), and `APP_ORIGIN` (exact application origin, HTTPS in production). The two `NEXT_PUBLIC_` values are public by design; never put a Google client secret, database password, or Supabase secret key in them. Restart or redeploy after changing values.
5. Test sign-in, callback, refresh, sign-out, profile edits, watched/unwatched, watchlist add/remove, and 1–10 ratings with two separate accounts. Verify that each account cannot read or mutate the other's rows through the Supabase Data API. Review Supabase logs, Auth settings, rate limits, data retention, and backup strategy before opening the feature publicly.

## Schema and authorization

`profiles.id` references `auth.users.id`. It stores a display name, an optional HTTPS Google-hosted avatar URL, and bounded JSON genre preferences. The Auth signup trigger creates a row and the migration backfills existing Auth users. `user_movie_status` is the equivalent of separate watched, watchlist, and ratings tables: its composite primary key `(user_id, content_type, content_id)` prevents duplicates, timestamps record watched and watchlist state, and `rating` is constrained to 1–10 only while watched. The `content_type` and stable ID key support future TV-series records without migrating personal keys, although this sprint's application accepts movies only. Partial indexes serve owner-scoped watched, watchlist, and rated queries.

Both tables enable RLS. Every SELECT, INSERT, UPDATE, and DELETE policy is scoped to `(select auth.uid()) = owner`. UPDATE also checks the new owner, so changing `user_id` or profile `id` cannot transfer a row. The client uses only the publishable key. Application routes derive user identity from `auth.getClaims()` and never accept a request-supplied user ID. Each mutation checks the exact application Origin, bounds and validates JSON, and verifies movie membership against the validated 1,100-ID catalogue. The database also checks stable ID syntax, content type, unique relationships, and rating rules. A user calling Supabase's Data API directly can create a syntactically valid but unknown ID in their **own** status table; the app does not render it. A future catalogue-ID registry and foreign key would close that data-quality gap when the catalogue is synchronized into PostgreSQL.

Supabase SSR keeps sessions in cookies. Next.js 16 `proxy.ts` refreshes them with `getClaims()` and forwards refreshed cookies and no-store headers. Cookies are configured HttpOnly, SameSite=Lax, and Secure on HTTPS because this app uses only a server-side Supabase client. Sign-out uses the local scope, leaving the person's other devices signed in. Personal API responses are private and no-store. Public catalogue and semantic search remain unchanged; Astra is read-only. No profile data is returned from public movie or search APIs.

## Operational limits

The application fetches status rows in 1,000-row pages for a signed-in account and enriches them with one validated catalogue snapshot, rather than querying one movie at a time. The initial UI covers 1,100 movies. At much larger per-user libraries, paginate the profile and watchlist UI instead of transferring every status row to the browser. Concurrent edits in multiple tabs use last-write-wins upserts; the primary key and rating constraint preserve valid state, but the last update can replace an earlier one. Add optimistic versioning if that use case becomes important.

Google OAuth and live RLS behavior remain unverified until credentials are supplied, the migration is explicitly approved and applied, and two-account acceptance tests run. Public deployment also needs distributed abuse protection for the existing search API. Movie plot redistribution rights remain unresolved; personal pages display metadata and source links only.
